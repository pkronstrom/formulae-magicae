# Firmware handoff and verification

**Minimum inputs.** Accepted revision-matched handoff, requirements, interface/pin mapping, device identity, power/timing constraints, programming and recovery and relevant open assumptions. An early experiment may use provisional I/O and known proxies. Keep experimental outcomes separate from accepted firmware.

**Implement.** Establish externally observable states and failures, then write small hardware adapters against the agreed interface. Pin build configuration and dependencies. Separate secrets and per-unit provisioning from the source and manufacturing bundle. Decide who programs the unit and who can recover it after an interrupted flash or update. Include production procedure or instructions only to the agreed scope.

Follow the [Docker build and verification procedure](docker.md) for a first experiment, a resumed build, and release evidence. Record the target or proxy, container image identity and platform, exact command and exported firmware hash in the manifest. Bind local simulation results to the binary actually loaded.

**Outputs.** Native source and pinned inputs, build manifest with hardware and firmware identifiers and hashes, flash/recovery instructions, relevant check reports, and a behavior/state visual. For Gadgetforge's `firmware` capture, use `firmware=<build manifest>` and `visual=<behavior view>` and register the actual sources, build artifacts and relevant evidence using `--uses`. Keep the paths relative to the project. The `firmware` check assesses the accepted behavior and hardware binding and includes fresh build/test evidence. Separate physical verification when it exists. If factory loading is in scope, provide the exact binary and applicable settings and prove the procedure to the extent required by the delivery brief.

**Iteration.** Recheck changed interface claims against the handoff. Route pin, power, board access or timing changes to the owning hardware phase. Preserve the originally accepted hardware version and identify the affected firmware evidence.

## Parallel PCB and firmware work

Pin the hardware contract revision (or hash) and list provisional interfaces before splitting work. The PCB agent owns the schematic, pin map and electrical constraints. The firmware agent owns the firmware directory or worktree, Docker build, board adapters, scenarios and screenshots. Agree on logical controls and display dimensions so UI work can proceed on a proxy while placement changes. Send pin, timing or peripheral changes back to the PCB owner. At integration, diff the pinned contract against the accepted handoff, update the board adapter and rerun the affected checks. One integrator captures phase evidence and regenerates the shared HTML board.

## Optional MCU emulation

When the target MCU lacks emulator support, a supported proxy can exercise the interaction. In the USB-key pilot, headless checks and an offline browser demo used the same compiled AVR flash bytes and display model. Drive the input pins and capture actual framebuffer pixels at asserted states. Include one negative action when consequential, such as cancelling a confirmation and checking that no output was sent. Record the exact loaded binary hash, simulator/version, scenario, mocked peripherals and the actions behind the screenshots. If a report names a HEX hash and simulation loads decoded flash, check both against the build manifest. Use the [recorded simulation strip](../../gadgetforge/references/project-board.md#simulated-ui-previews) even while the production phase awaits its hardware handoff.

Use an emulator for a behavior you want to exercise before the hardware arrives. Check support for the exact target chip and the specific peripherals involved, including the variant and bus mode. Suitable options include:

- **Wokwi** for interactive firmware with virtual buttons, displays or sensors. It covers several ESP32 variants, classic AVR Arduinos and Raspberry Pi Pico boards. Build the target firmware and model the wiring in `diagram.json`, with the binary selected in `wokwi.toml` for external builds. For repeatable checks, its CLI can play button or sensor scenarios and check serial output. CLI simulation sends the binary to the Wokwi service and requires a token. [Supported hardware](https://docs.wokwi.com/getting-started/supported-hardware), [project configuration](https://docs.wokwi.com/vscode/project-config), [CLI usage](https://docs.wokwi.com/wokwi-ci/cli-usage), [cloud execution](https://docs.wokwi.com/wokwi-ci/getting-started)
- **Espressif QEMU** for local ESP-IDF boot and debugging on supported targets, such as ESP32-S3. Check the peripheral coverage before choosing a test. **simavr** is a local command-line option for classic AVR firmware, such as ATmega328-based projects. [Espressif QEMU](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/tools/qemu.html), [simavr](https://github.com/buserror/simavr)

For the password manager example, simulate navigation and confirmation with dummy entries, virtual buttons and a compatible OLED. Record the firmware hash, emulator and configuration, stimulus or scenario, expected behavior and observed result. Espressif hardware features and their emulated equivalents can differ. For example, Wokwi's ESP32 USB feature table documents CDC serial support. Keep actual USB keyboard enumeration, electrical behavior and real-device recovery for bench testing unless the particular emulator and test exercise that exact behavior. Emulated evidence stays optional and does not gate ordinary hardware release. [Wokwi ESP32 peripheral coverage](https://docs.wokwi.com/guides/esp32#simulation-features), [automation scenarios](https://docs.wokwi.com/wokwi-ci/automation-scenarios)

For a UI review, capture the virtual display at meaningful steps in the scenario, with the input that led to each state. Save the screenshots with the run, firmware revision and display model so the review board or PDF booklet can show the same sequence. Wokwi's CLI can save a screenshot of a simulated display. Label it as simulated. Use dummy data and keep real credentials out of the UI fixtures and screenshots. [Wokwi CLI screenshot options](https://docs.wokwi.com/wokwi-ci/cli-usage#automation)

For a headless capture, run `wokwi-cli . --scenario <scenario.yaml>` from the simulator project. Use scenario steps to drive the controls, wait for the intended state and save each display PNG with `take-screenshot`. The same step can compare against a baseline when a screen is specified closely enough for a regression check. Keep the scenario, display PNGs and a run record tied to the firmware hash. Use those artifacts for the [offline review board](../../gadgetforge/references/project-board.md#simulated-ui-previews) and optional PDF. [Wokwi automation scenarios](https://docs.wokwi.com/wokwi-ci/automation-scenarios)

### Hands-on review during development

Offer a runnable draft as soon as the user can try a meaningful interaction. Provide the build revision, a starting state and one or two things to try. For example, use dummy entries to try selecting an item, cancelling, and returning to the list. Use an approved Wokwi browser project link or give the user the project's local simulator configuration and launch instructions. [Wokwi project sharing](https://docs.wokwi.com/), [Wokwi for VS Code](https://docs.wokwi.com/vscode/getting-started)

Collect feedback against that draft in the board or conversation. Ask for the action, what the device showed, and what the user expected. Reproduce the report against the same build, update the behavior and turn a reproducible fix into a scenario check where useful. Refresh the review visual with the new build. The user can revisit this loop as firmware evolves. Keep the review optional and use the hardware change process if feedback requires changing an interface.
