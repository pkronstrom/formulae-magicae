# Hardware handoff to firmware

For programmable hardware, carry loading, boot, debug where needed, recovery and production access obligations from architecture through schematic, layout and enclosure. Design the route before the board becomes hard to change. The Espressif recipe illustrates which evidence to collect.

**Capture `firmware-handoff`.** Minimum inputs are current routed PCB and applicable enclosure inputs, accepted requirements and the programming obligations. Output roles `handoff` (versioned hardware handoff) and `visual` (pin map or annotated programming access). Include hardware identity, exact MCU/module and package, schematic and pin map, power/IO domains, timing, peripherals, cable or jig, programming/recovery/debug access, interaction goals, current assumptions and unresolved obligations. The `handoff` check reconciles all of those against the actual hardware. Keep physical function marked untested when no board was exercised.

For the usual prototype, release and order the hardware once its design is ready. Prepare the handoff once the hardware is defined. Give it to `gadgetforge-firmware` when implementation is in scope, build while the hardware is being made or after it arrives, then verify on the real board. The hardware package can be released before either firmware phase. Enable the build later with `configure --firmware build` without reopening the hardware solely because the firmware scope changed. If the work uncovers a real hardware change, return to the owning phase.

If an order includes factory loading, enable `--factory-programming` along with `--firmware build`. That release requires the accepted build containing the exact image and agreed loading instructions. Plan a separate first article if the order needs real-board verification before factory loading. Distinguish builds and simulator evidence from physical verification. For an analog project, use `--firmware none` so both firmware phases are inapplicable.

If another agent starts firmware in parallel, share a revision-pinned interface contract and designate one owner of the shared board and phase records. Follow the sibling skill's [parallel work guidance](../../gadgetforge-firmware/references/handoff.md#parallel-pcb-and-firmware-work). Publish proof-of-concept screenshots through the [simulation strip](project-board.md#simulated-ui-previews) before the production build is eligible for capture.
